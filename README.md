# Simulated Trading Platform (v2)

A **simulation-only** multi-market trading platform: one Node.js server serves the
API, the WebSocket feed and the browser UI. Prices are generated by the server,
balances are virtual demo money, and every market payload is labelled
**SIMULASI** — in the API *and* in the UI.

> ⚠️ **No real money.** There are no live accounts, no deposits, no withdrawals,
> no QRIS/bank transfers and no payment gateway. The `payments/` module exists as
> an architectural seam and returns `501 NOT_AVAILABLE` ("belum tersedia").
> Operating a real-money derivative platform requires permits and licensing under
> the applicable local regulations (in Indonesia: Bappebti/OJK); do not point this
> code at real funds.

## Markets

| symbol | name | price decimals | character |
| --- | --- | --- | --- |
| `ASIA_COMPOSITE` | Asia Composite Index | 2 | a fictional Asian index, calm |
| `CRYPTO_COMPOSITE` | Crypto Composite Index | 2 | a fictional crypto basket, faster |
| `DOGE` | Dogecoin (simulated) | 5 | a simulated DOGE/USDT series, wild |

All three are invented price series. `DOGE` only borrows the name of the coin.

## Features

**Public market data** — `/api/v1/markets`, ticker with 24 h change, candles for
`5s · 15s · 30s · 1m · 5m · 15m · 1h`, recent ticks, and a WebSocket feed that
pushes ticks, forming candles and `candle_closed` events per market/timeframe.

**Trading** — stake any amount inside the admin limits, choose 5 s … 8 h
(presets 5s/10s/15s/30s/1m/5m/15m/30m/1h/2h/4h/8h), BUY (up) or SELL (down),
preview payout and potential profit, confirm in a dialog that shows market,
direction, amount, duration, entry price, expiry and payout. Open trades show a
countdown, entry price, live price and estimated result; closed trades show
win/lose/draw, payout and time. Entry/expiry markers are drawn on the chart.

**Accounts** — registration with argon2id password hashing, email verification
(dev mode prints the link), login/logout with an httpOnly JWT cookie,
forgot/reset password, per-user demo wallets in **USD, IDR and USDT**, display
currency, demo balance summary and a reset button.

**Admin** — dashboard (users, trade volume, payouts, simulated profit), market
controls (trend up/down/neutral, volatility, mood `sepi|normal|cepat|liar`,
pause/resume, open/close), trade list with filters and manual settlement
(reason required), user search/detail/balance adjustment/block, settings (payout
rate & mode, allowed durations, amount limits, starting balance, FX rates, demo
top-up caps) and a full audit log.

**Engineering** — SQLite with migrations and a seed, `BEGIN IMMEDIATE` balance
checks, idempotent trade creation, restart-safe settlement, zod validation on
every input, helmet + strict CORS, rate limits, structured pino logging,
`/healthz`, and 123 automated tests (unit, integration, WebSocket, browser).

## Stack

* Node.js ≥ 20 (developed on 22), TypeScript (ESM), Express 4
* SQLite via **better-sqlite3**; if its native binding is unavailable on the host
  the server transparently falls back to the built-in `node:sqlite` driver
  (same code path, reported by `/healthz` as `dbDriver`)
* `ws` for realtime, `zod` for validation, `argon2` for passwords,
  `jsonwebtoken` for sessions, `helmet`/`cors`/`express-rate-limit` for hardening,
  `pino` for logs
* Frontend: **vanilla ES modules** + a canvas chart adapted from the supplied
  chart-kit (no framework, no CDN, no external fonts — works offline)

## Install

```bash
git clone <repo> && cd trading
npm install                 # if a sandbox blocks native builds: npm install --ignore-scripts
cp .env.example .env
```

`better-sqlite3` needs a prebuilt binary or a C++ toolchain. If neither is
available the app still runs on Node's built-in SQLite driver — no code change
required.

## Environment

Everything is validated at boot (`src/config.ts`). See `.env.example`; the
important ones:

| variable | default | notes |
| --- | --- | --- |
| `NODE_ENV` | `development` | `production` enforces the safety checks below |
| `PORT` / `HOST` | `3000` / `0.0.0.0` | |
| `SQLITE_PATH` | `./data/simulated-trading.sqlite` | file is created on boot |
| `JWT_SECRET` | dev fallback | **required** ≥ 32 chars in production |
| `SESSION_TTL_SEC` | `43200` | cookie + JWT lifetime |
| `COOKIE_NAME` / `COOKIE_SECURE` | `sim_session` / `false` | set `COOKIE_SECURE=true` behind HTTPS |
| `APP_PUBLIC_URL` | `http://localhost:3000` | used to build email links |
| `CORS_ORIGINS` | `http://localhost:3000,http://127.0.0.1:3000` | comma separated; never `*` with credentials |
| `ADMIN_EMAIL` / `ADMIN_USERNAME` / `ADMIN_PASSWORD` | `admin@simulator.local` / `admin` / `admin-demo-123` | seed admin; **must change in production** |
| `DEV_EMAIL_LINKS` / `EXPOSE_DEV_TOKENS` | `true` / `true` | print + return verification/reset links; forced off in production |
| `REQUIRE_EMAIL_VERIFICATION` | `false` | set `true` to block trading before verification |
| `PAYOUT_RATE` / `PAYOUT_MODE` | `0.85` / `profit` | initial runtime settings (admin-editable) |
| `TICK_RETENTION_DAYS` | `7` | ticks are pruned in the background |
| `SETTLE_INTERVAL_MS` | `250` | expiry settlement loop |
| `WS_TICK_MAX_PER_SEC` | `15` | per-client tick coalescing |
| `RATE_AUTH_MAX` / `RATE_TRADE_MAX` / `RATE_GLOBAL_MAX` | 20 / 30 / 1200 per minute | |

Production startup refuses to boot when `JWT_SECRET` is missing/short, when the
default admin password is unchanged, or when dev token exposure is enabled.

## Migrations & seed

The server migrates and seeds automatically on boot. Explicitly:

```bash
npm run migrate     # applies migrations/sqlite/*.sql (idempotent, tracked in schema_migrations)
npm run seed        # 3 markets + default settings + initial admin (idempotent)
```

On an empty database the first boot also generates **24 h of synthetic candles
and ticks per market**, so charts and the 24 h change are meaningful immediately.

```bash
npm run dev         # tsx watch src/server.ts (http://localhost:3000)
npm run typecheck   # tsc for src + tests

npm run test:watch
```

Open <http://localhost:3000> → the trading page. Registration creates the three
demo wallets; the verification link is printed in the server log and returned to
the browser in dev. The seeded admin is listed in `.env.example`.

Because the UI is served by the same origin, no proxy is needed. If you prefer a
separate dev origin, add it to `CORS_ORIGINS` (WebSocket origin checks use the
same list).

## Production

```bash
npm ci
npm run build            # tsc -> dist/
NODE_ENV=production \
JWT_SECRET="$(openssl rand -base64 48)" \
ADMIN_PASSWORD="a-strong-unique-password" \
COOKIE_SECURE=true \
APP_PUBLIC_URL="https://your.host" \
CORS_ORIGINS="https://your.host" \
npm start                # node dist/server.js
```

Checklist before exposing it:

* TLS terminated in front (nginx/Caddy); set `COOKIE_SECURE=true` and
  `TRUST_PROXY=true` when behind a reverse proxy.
* Rotate `ADMIN_PASSWORD`, set a unique `JWT_SECRET`.
* Keep `DEV_EMAIL_LINKS=false` / `EXPOSE_DEV_TOKENS=false` (enforced).
* Back up the SQLite file (`data/*.sqlite`); WAL mode is enabled.
* `/healthz` for the supervisor; send `SIGTERM` for a graceful shutdown (flushes
  ticks/candles, closes sockets, settles nothing that is not due).
* Only one process may own the database file; the app is single-writer by design.

## Safe defaults for decisions the spec left open

The spec asked for a safe default plus a note. These are the choices made:

1. **Money precision.** Balances are stored as integer *minor units*
   (USD/USDT = cents, IDR = whole rupiah). Client amounts are major units and
   converted once, at the edge.
2. **Tie handling.** Server-quantised `close == entry` is a **draw**: the stake is
   refunded and no profit is paid. Direction has no tie-breaker.
3. **Payout.** Default mode `profit` (rate `0.85` = 85 % of the stake as profit).
   Admin can switch to `total` (rate = total return) — then the rate must be > 1.
   The rate is snapshotted per trade, so later admin changes do not rewrite
   history.
4. **Settlement price.** The last server tick at or before `expiry_time`. If no
   such tick exists (server down for the whole window), the trade is refunded at
   entry price.
5. **Trade entry price.** Latest server tick at insertion; a trade cannot open
   while a market has no price yet (`409`).
6. **Email verification.** Optional by default (`REQUIRE_EMAIL_VERIFICATION=false`)
   so the demo is usable immediately; the flow itself is complete.
7. **Demo FX rates.** `1 USD = 16,000 IDR`, `1 USDT = 1 USD`, admin-editable. Used
   for display and demo conversions only — never for settlement (a trade settles
   in the currency it was placed in).
8. **Demo top-up.** Instant, virtual, capped per transaction (`topupMax`) and per
   day (`topupDailyCount`, default 5). No QRIS/bank flow anywhere.
9. **Demo balance reset.** Restores the admin starting balance and voids open
   trades at entry price (refund), so the reset cannot be used to extract a
   payout.
10. **Blocking a user** revokes all sessions immediately (`token_version` bump)
    and blocks login. Admin accounts cannot be blocked.
11. **Idempotency.** Optional `Idempotency-Key` on `POST /trades`; a replay with
    the same payload returns the original trade (`200`, `Idempotent-Replayed`),
    a different payload returns `409`.
12. **Market state.** `active=false` = closed (no trading, no ticks). `paused=true` =
    temporarily no trading while the feed/expiry keeps running. Both are visible
    in every market payload.
13. **Ordering of gates.** Validation → market open → paused → duration →
    amount → open-trade limit → balance, inside one transaction for the last two.
14. **Max open trades** per user defaults to 10 (protects the demo from abuse).
15. **Timestamps** are always the server clock; the browser only formats them.
16. **Logout is stateless** (the cookie is cleared; the JWT expires). Password
    change/reset/block revoke every session.

### Assumptions

* `ASIA_COMPOSITE` and `CRYPTO_COMPOSITE` are **composite indices** invented for
  this exercise (a plausible level, two decimals); `DOGE` is a simulated
  DOGE/USDT series with five decimals because DOGE-like prices trade far below 1.
* Market mood/volatility only shape the random walk; they are not a prediction
  and are labelled SIMULASI everywhere.
* Mixed-currency totals on the admin dashboard are reported in minor units and
  are informational only — a production implementation would report per currency.
* The 24 h change uses the tick nearest to 24 h ago (falling back to the oldest
  available tick), so a fresh install still shows a number.
* One process per database file is assumed (single-writer SQLite).
* The DOM smoke test uses jsdom with a stubbed 2D canvas context: it verifies the
  UI wiring, not pixel output.

## Security notes

* Prices, timestamps, expiry and trade results are computed server-side; the
  client cannot influence them.
* Balance check + debit + trade insert run in one `BEGIN IMMEDIATE` transaction,
  backed by `CHECK (balance_minor >= 0)`.
* Passwords: argon2id. Sessions: HS256 JWT in an httpOnly, SameSite=Lax cookie
  (Bearer supported for API clients). `SameSite=Lax` plus same-origin-only
  requests mitigates CSRF; add a CSRF token if you ever accept cross-site writes.
* Every input goes through zod; unknown fields are rejected on admin settings and
  market patches.
* Admin endpoints re-check the role from the database on every request.
* helmet with a strict CSP (`default-src 'self'`, no inline script/style),
  HSTS in production, no `x-powered-by`, a strict CORS allow-list and rate limits
  on auth/trade/global scopes.
* Structured logging with password/cookie/authorization redaction.

## Known limitations / next steps

* `payments/` is a stub by design (real-money accounts, QRIS, payouts).
* No KYC, no 2FA, no email provider (dev mailer only), no multi-process scaling.
* Tick history retention is 7 days; candles 30 days; audit 90 days.
* Native SQLite is preferred; the `node:sqlite` fallback prints an
  `ExperimentalWarning` on Node 22.
